# Архитектура и обновления

Статус: механизм Analyzer, адаптер и словарный слой реализованы на этапе 2.
Git reader, сравнение деревьев и подготовка текста реализованы на этапе 3.
Внутренний [scan pipeline](scan-api.md) реализован на этапе 4.
CLI, JSON/HTML writer, runtime validation и baseline подключены на этапе 5.
[Штатный Docker/Compose](user/README.md) и [пример Jenkins](admin/jenkins.md)
подключены на этапе 6; реальные Jenkins/GPU не проверялись.

## Компоненты и данные

| Компонент | Вход / выход | Ответственность |
| --- | --- | --- |
| `scanner` | Git-деревья, доверенный профиль и baseline → JSON/HTML | CLI, охват, декодирование, HTTP-клиент, координаты, контроль результата |
| `analyzer` | Исходный текст → сущности/смещения | Presidio, правила, NER, длинный текст, source metadata |
| Словарный адаптер scanner | Исходный текст и закреплённые правила → находки | Совпадения бизнес-терминов вне Analyzer с исходными координатами |

Поток: параметры → разрешение коммитов → манифест дерева → проверка baseline
и профиля → выбор полных файлов → декодирование → Analyzer и словарь →
проверка ответа/координат → находки → полнота и assurance → JSON/HTML/exit code.
Сбой любого обязательного компонента не даёт успешный результат.

Git-репозиторий читается из mount `/input/repository:ro`; выход `/output` отдельный.
Внутренняя сеть Docker соединяет только scanner/analyzer, порт Analyzer не
публикуется. Модель и библиотеки находятся в образе. Внешних API и загрузки
зависимостей при сканировании нет. Готовность Analyzer проверяется до работы,
совместимость подписи контролируется до завершения запуска.

CLI/Git/отчёты не импортируют внутренний серверный код Analyzer. Изменение
модели не должно требовать переписывания чтения Git. Общая модель находок
принимает новые строки категорий/источников.

Внутренний [Git API](git-reader.md) состоит из `git_repository`, `git_plan`
и `text_policy`. Первый создаёт изолированный metadata-view и проверяет
OID объектов, второй фиксирует выбор полных файлов по A/B, третий применяет
scope/классификацию/кодировки. Подготовка итеративна; `ready` означает наличие
полного текста, не выполненный анализ. Исходная конфигурация не становится
конфигурацией Git reader. Ограничения layout и неизменности object store
зафиксированы в [ADR-0003](decisions/0003-isolated-git-reader.md).

`configuration` формирует строгий эффективный профиль, `engine` проверяет
locks/словарные assets и вычисляет идентичность, `findings` проверяет значения,
строит координаты/контекст и стабильные ID. `pipeline` соединяет эти компоненты
через ограниченную очередь и owning Git thread. Результат файла принимается
после обоих обязательных слоёв; отмена дожидается локальных потоков.
[ADR-0004](decisions/0004-bounded-scan-pipeline.md) фиксирует границы памяти,
дедлайнов и атомарности. Проверка технического соответствия механизму отделена
от независимых метрик распознавания на коде.

`baseline` сверяет чистый предыдущий отчёт с profile и реальным деревом A;
`reports` строит JSON v1, `report_validation` проверяет schema/semantic
инварианты, `html_report` формирует автономный безопасный HTML, `output`
резервирует пустую папку и атомарно публикует отдельные файлы. CLI связывает
компоненты, сохраняя values/context в артефактах и безопасную сводку в консоли.
[ADR-0005](decisions/0005-trusted-baseline-and-artifacts.md) описывает доверие
и ограничения частичного отказа записи.

`scripts/docker_scanner.py` — host launcher без сторонних Python-зависимостей.
Он проверяет deployment Image IDs, генерирует уникальный Compose JSON и владеет
cleanup точного project label. Non-root сервисы имеют только internal network,
read-only FS/вход, tmpfs и output; logs отключены. Online prepare и offline build/
export/import отделены от scan. Infrastructure failure имеет приоритет над
прежним clean артефактом; [ADR-0006](decisions/0006-offline-container-lifecycle.md).

## Подготовка upstream

`upstream.lock.json` содержит `lock_version`, URL и полный SHA прокси,
модель/ревизию/контрольные суммы файлов, patchset SHA-256, SHA-256 словаря
и профили зависимостей. Digest фактически собранного платформенного образа
хранится отдельно в runtime lock, после сборки и проверки артефактов.
В отчёте `analyzer_image_digest` — идентификатор конкретного
платформенного образа из `docker image inspect --platform`. У классического
image store это digest конфигурации, у проверенного Docker 29/containerd —
digest платформенного OCI manifest. Общий multi-platform index не используется
как подпись поведения. Runtime lock отдельно хранит локальную неизменяемую
`image_reference_id` для запуска с явным `--platform`, `image_id_kind` и
descriptor. Registry RepoDigests записываются отдельно при наличии.
Неизвестный digest до сборки хранится только в промежуточном манифесте;
финальный runtime lock не принимает пустые значения. Source lock фиксирует
97 файлов исходников/синтетических тестовых данных, patch hashes, точные
constraints CPU ARM64 и хеш дерева spaCy. `seal` выполняет probe без сети,
сверяет все версии/артефакты и только затем атомарно пишет runtime lock.

Исходники экспортируются из конкретного коммита в отдельный build context
через Git, из локального клона или при явном получении ревизии на этапе
подготовки. Незакоммиченные файлы, `.env`, рабочие secrets и локальные credentials
в контекст не включаются. Сертификаты/настройки сборки передаются отдельно
явным действием оператора, как в окружении прокси.

Сборка переиспользует Dockerfile и полный согласованный комплект Analyzer.
Ограниченные адаптации scanner хранятся отдельно в `patches/`; патч выдачи
источника не должен менять детекторы. Проверяется применение без неявного
fuzz и итоговые контрольные суммы. Сервер upstream в соседнем проекте не меняется.
Словарный адаптер использует закреплённые правила и семантику совпадения,
а не новый независимо расходящийся список терминов.

Готовые образы переносятся в закрытую среду отдельно от запуска. Локальный
соседний клон не требуется при работе готовых образов. CPU — основной профиль,
GPU использует возможности прокси; fallback GPU→CPU при отказе не допускается.

## Обновление и откат

1. Выбрать конкретную новую ревизию и просмотреть изменения детекторов,
   словаря, API, лицензий и зависимостей.
2. Подготовить исходники, применить адаптационные патчи, собрать образ
   и проверить модель/артефакты; не обновлять штатный lock заранее.
3. Проверить health/API, каталог сущностей, метаданные источников,
   соответствие исходному механизму и корпус scanner.
4. Сохранить результаты и зафиксировать новый lock/образ явным изменением.
5. Выполнить новый полный snapshot: старые baseline не переиспользуются.

Откат возвращает прежние lock, образы и профиль. Baseline допустим только
при совпадении прежнего профиля и проверяемого состояния; отчёт от новой
версии не становится автоматически совместимым. Если API изменился,
адаптируется его клиентский слой; исходники распознавания не переписываются
разрозненными копиями внутри scanner.

На этапе 7 проверена согласованная историческая репетиция реальных версий
v0.4.0 → da4f50a → v0.4.0 с отдельными context/locks/images. Один scanner wheel
работал с обоими engine bundles, несовместимые baseline отклонялись, прежний
profile восстанавливался. Штатные locks не менялись. [Процедура и evidence](admin/updating-analyzer.md).

## Доверие и решения

Репозиторий и HTTP-ответы обрабатываются как данные. Конфигурация, lock,
образы и baseline поступают из доверенного процесса; JSON Schema проверяет
форму, но не подлинность. Детали — [SECURITY](../SECURITY.md).

[ADR-0001](decisions/0001-analyzer-boundary.md) фиксирует границу Analyzer,
[ADR-0002](decisions/0002-state-and-baseline.md) — конечные состояния и baseline.
[Инвентаризация upstream](reference/detection.md) отделяет проверенные факты от дизайна.
