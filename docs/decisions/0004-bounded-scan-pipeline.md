# ADR-0004: Ограниченный pipeline и атомарный результат файла

Статус: принято планом [этапа 4](https://github.com/vovkins/ru-llm-scanner/issues/7),
реализовано 2026-10-19.

## Контекст

Git/text и Analyzer/словарь реализованы независимо. Репозиторий может содержать
много файлов, а оба детектора обязательны. Подготовленный текст нельзя выдавать
за выполненный анализ; потеря одного слоя не должна давать чистый результат.
Git reader последователен, синхронная CPU-работа не должна блокировать event loop.

## Решение

Использовать один owning thread для Git, ограниченную asyncio queue и `c`
workers, CPU pool до `c` потоков для словаря/координат. Держать до `2c+1`
подготовленных полных текстов, сохраняя весь манифест и результаты в памяти.
Анализировать исходный текст обоими слоями и принимать файл только после
валидации всех находок. При ошибке отбросить незавершённые кандидаты этого
файла, сохранить завершённые другие файлы и вернуть неполный результат.

Readiness обязателен до работы даже для пустого входа, подпись проверяется
до конца. Нет retry анализа или fallback. При отмене дождаться выполняющегося
локального синхронного кода и закрыть ресурсы; поздний успех не проходит deadline.
Ошибки публичного результата содержат машинный код, а не текст исключения.

## Следствия

Ограничено число одновременно подготовленных текстов, но не общая память
модели/манифеста/находок. Очистка CPU-потока может продлить фактический возврат
после timeout; остановка HTTP не равна отмене вычисления сервером. Это явно
документировано в [scan API](../scan-api.md). Потребность в process isolation
и жёстком общем RAM/time budget потребует отдельного решения.

Техническое соответствие pipeline исходному механизму и качество детекторов
на независимом корпусе проверяются раздельно. Измеренные ошибки качества
сохраняются, не исправляются ослаблением теста или скрытой сменой правил.
