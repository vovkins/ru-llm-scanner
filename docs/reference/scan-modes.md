# Режимы, Git и охват

Git-снимки/сравнение и подготовка текста реализованы как
[внутренний API](../git-reader.md) и подключены к работающим [CLI](../cli-quickstart.md),
детекторам и отчётам. Читается содержимое объектов
Git, а не текущих файлов рабочей папки. Репозиторий не переключается и не меняется.

## Выбор состояния

`snapshot --commit B` перечисляет все недиректориальные записи дерева B.
`diff --from A --to B` сравнивает ровно деревья A и B и анализирует целиком
новые и изменённые файлы B. Автоматического merge-base или обхода истории нет.

Ревизии разрешаются один раз в полные commit OID, после этого чтение идёт по
OID. Допустимы коммиты, ссылки и теги, разрешаемые в коммит; деревья без коммита,
неоднозначные/недоступные ревизии и значения, начинающиеся с `-`, отклоняются.
Git object format определяется репозиторием: SHA-1 либо SHA-256.

Достаточно иметь локально A, B и все требуемые деревья/объекты. Полная история
и проверка отношения предок/потомок не требуются для сравнения состояний.
Shallow clone допустим при доступности этих объектов; missing/promisor-объект
даёт ошибку. Скрытые fetch и partial-clone lazy fetch запрещены.
Незакоммиченные, staged и неотслеживаемые изменения не влияют на результат.

## Изменения

Сравнение основано на сырых путях, Git mode и object OID. Неизменённой считается
запись с теми же путём, mode и OID. Смена executable bit также выбирает файл
для повторной проверки. Смена обычного файла на ссылку/подмодуль отражается
как `type_changed` и проходит новую классификацию.

Переименованный файл всегда проверяется по новому пути. Для одинакового
содержимого возможно обозначение `renamed`: пары удалённый/добавленный путь
с одинаковыми mode/OID связываются в порядке сырых байтов пути. Переименование
с изменением содержимого допустимо отражать как удаление и добавление.
Эвристика сходства Git не влияет на то, какие файлы проверены.

Удаления сохраняются в `deleted_files`, вне манифеста B. Внутренний план
сохраняет все удалённые пути A, включая старый путь exact rename. В merge-коммите
проверяется итоговое дерево B относительно явно переданного A. При A = B
новых файлов нет: совместимый baseline подтверждает прежний охват, без него
отчёт говорит только об отсутствии изменений. Пустое дерево даёт нулевой охват
текста, явно видимый в счётчиках; неготовность Analyzer не скрывается даже тогда.

## Классификация файлов

Все пути дерева B присутствуют в `files`, в том числе не выбранные для анализа.
Каталоги отдельно не учитываются. Записи имеют один из статусов:

| Статус | Смысл |
| --- | --- |
| `analyzed` | Полный текст обработан в текущем запуске, включая пустой файл |
| `inherited` | Подтверждение неизменённого текста перенесено из совместимого baseline |
| `unverified` | Неизменённая запись без baseline, текущий diff её не проверял |
| `excluded` | Путь вне явно заданного include/exclude |
| `unsupported` | Объект вне текстовой области первой версии |
| `error` | Объект должен проверяться, но обработка не завершена |

Сначала применяются явные ограничения путей, затем классификация типа.
Расширение само по себе не исключает файл: обычный текст, переименованный
в `.pdf` или `.zip`, проверяется. Контейнеры определяются по содержимому;
если совпадает сигнатура формата вне области, встроенный текст не извлекается.
Git LFS pointer отмечается
как `lfs_pointer`; данные LFS не читаются и не скачиваются. Mode `160000` —
`submodule`, mode `120000` — `symlink`; ссылка не разыменовывается.

Поддерживаемые кандидаты: исходники, конфигурации, документация, скрипты,
lock-файлы и файлы без расширения. Скрытые файлы и закоммиченные пути из
`.gitignore` не исключаются. Ни `vendor`, ни тесты не исключаются автоматически.
Правила распознавания контейнеров и классификации текста имеют версию
`text-v1`; её изменение инвалидирует baseline. Для начальной классификации
достаточно первых 8192 байтов объекта; этот предел не ограничивает анализ
полного поддерживаемого текста.

| Содержимое | Классификация `text-v1` |
| --- | --- |
| `%PDF-` с начала | `pdf` |
| ZIP `PK` + `03 04`, `05 06` или `07 08`; gzip `1f 8b`; 7z `37 7a bc af 27 1c`; RAR `Rar!` | `archive` |
| `ustar` по смещению 257 | `archive` (tar) |
| OLE `d0 cf 11 e0 a1 b1 1a e1` | `office` |
| PNG `89 50 4e 47 0d 0a 1a 0a`; JPEG `ff d8 ff`; `GIF87a`/`GIF89a`; TIFF `II 2a 00`/`MM 00 2a`; RIFF + `WEBP` по смещению 8 | `image` |
| Канонический LFS pointer: строка version URL Git LFS v1, `oid sha256:` + 64 hex, `size` + целое | `lfs_pointer` |

ZIP-based Office помечается `archive`; причина — представление, содержимое
в любом случае вне области. LFS распознаётся по полному малому pointer-файлу
(до 8192 байтов, допускаются стандартные extension-строки), не по одному слову
`version`. Неизвестный контейнер не исключается по догадке об энтропии.
SVG/XML без указанных сигнатур остаются кандидатами текстового анализа;
расширение `.svg` не исключает файл. Большой векторный файл может потребовать
значительного CPU-времени, хотя визуальный анализ изображений не выполняется.

Декодирование: сначала BOM (UTF-8/16/32), затем UTF-8, либо явно назначенная
кодировка пути. UTF-32 BOM проверяется раньше UTF-16. Декодирование строгое,
без `ignore`/`replace`. Непустой файл с NUL вне распознанной Unicode-кодировки
считается бинарным. Остальные кандидаты, которые не удалось декодировать,
дают `decode_error`, а не молчаливый пропуск. Для неоднозначного файла
оператор задаёт кодировку явно. Возможность скрытых данных в бинарных и
специально закодированных объектах остаётся за границами текстового аудита.

`excluded`/`unsupported` не делают заранее оговорённую текстовую проверку
неполной, но видны с причинами; на их содержимое результат не распространяется.
Превышение лимита выбранного текстового файла, timeout и ошибка декодирования
дают `error`, итог `2`. Расширения и заголовки недоверенны; критерии `text-v1`
проверены на синтетическом корпусе этапа 3. Это классификация заданной области,
не гарантия выявления любых замаскированных форматов.

Некорректные сырые пути (абсолютный путь, NUL, пустой сегмент, `.` или `..`)
отклоняются с ошибкой дерева; отображение пути не используется для открытия
файлов на хосте.

## Полнота и координаты

`coverage.complete` означает завершённость заданной проверки, не аудит
всех возможных форматов и не стопроцентную полноту детекторов. В обычном diff
она может быть `true` при `unverified > 0`: изменённые файлы обработаны,
но весь B не подтверждён. Это отражается в `result.assurance=changed_files_only`.

После удаления BOM текст не нормализуется: CRLF, пробелы, Unicode и переводы
строк передаются детектору без замены. Смещения — индексы Unicode code point
Python, интервал `[start, end)`. Строки и столбцы — с 1, конец исключающий.
CRLF считается одним разделителем строк, одиночные CR и LF — также разделители.
Столбцы считают code points, не байты, графемы или экранную ширину tab.
Контекст — полные строки находки плюс заданное число соседних строк.

Git-пути могут содержать не-UTF-8 байты. Их идентичность задаётся
`path_bytes_b64` (канонический Base64 сырых байтов относительного пути).
`path` — отображение через UTF-8 с `backslashreplace`; оно не используется
для чтения, сопоставления baseline или HTML-идентификаторов. Сортировка — по
сырым байтам пути. Управляющие символы экранируются при отображении.

## Матрица поведения

| Сценарий | Проверяемые файлы | Результат |
| --- | --- | --- |
| Первый аудит B | Все поддерживаемые файлы B | `snapshot_verified`, если обработка завершена |
| Секрет в добавленном файле | Весь новый файл B | Находка с координатами в B |
| Изменилась соседняя строка | Весь изменённый файл B | Значение вне добавленной строки также может быть найдено |
| Переименование | Файл по новому пути | Повторный анализ, без потери места |
| Удаление файла | Ничего из удалённого содержимого | Запись в `deleted_files` |
| Секрет появился и удалён между A/B | Только итоговые отличия B | История не проверена, секрета может не быть в отчёте |
| Новый детектор, прежний baseline | Полный snapshot нужен заново | Предъявленный baseline отклоняется |
| Нет baseline, есть неизменённые файлы | Только изменённые текстовые файлы | `changed_files_only`, неизменённые `unverified` |
| Нет объекта / сбой Analyzer | Обработка не завершена | Код `2`, assurance `none` |
| PDF / LFS / подмодуль / ссылка | Содержимое не проверяется | Явный `unsupported` с причиной |
| Текст превышает лимит | Нельзя считать обработанным | `file_too_large`, код `2` |
