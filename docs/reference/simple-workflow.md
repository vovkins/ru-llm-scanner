# Простой интерфейс сборки и сканирования

**Спецификация этапа [#39](https://github.com/vovkins/ru-llm-scanner/issues/39),
общий план [#38](https://github.com/vovkins/ru-llm-scanner/issues/38).
Build/scan/diff реализованы на этапе [#40](https://github.com/vovkins/ru-llm-scanner/issues/40);
suite `make test` ещё не готов и явно возвращает 2.** Это контракт для этапов 2–4,
не инструкция запуска опубликованного v0.2.0. Прежний explicit путь:
[сборка](../admin/build.md), [сканирование](../user/README.md).
[ADR-0007](../decisions/0007-simple-workflow.md) объясняет границу интерфейса;
[карта существующих шагов и матрица приёмки](../../verification/simple-workflow-stage-1/README.md)
отделяет проект от фактически выполненных проверок.

## Первый запуск

Сборочный сервер имеет интернет. Оператор работает из доверенного checkout
scanner; входной Git-клон передаётся параметром и никогда не становится местом
поиска исполняемых файлов, Makefile или конфигурации установки.

Основной сценарий из checkout с реализацией этапа 2:

```sh
make build
make scan REPO='/srv/git/example project'
```

После scan выводятся результат, абсолютные пути `report.json` и `report.html`.
Отдельные setup, doctor, up/down, offline/export/import цели для этого пути
не вводятся. Существующие низкоуровневые команды переноса сохраняются.

## Предпосылки и границы

| Что готовит оператор хоста | Что делает инструмент |
| --- | --- |
| POSIX, Python 3.11+ с venv/pip, Git, GNU Make 3.81+ | Проверяет версии; создаёт отдельное сборочное Python-окружение |
| Rootful Docker с platform inspect API 1.49+ и Compose v2+, BuildKit | Проверяет доступ, платформу, локальные images и совместимость |
| Non-root учётная запись с доступом к Docker и bind-путям | Запускает контейнеры с UID/GID оператора и текущей изоляцией |
| Доступ сервера сборки к одобренным источникам и достаточные ресурсы | Получает закреплённые материалы, проверяет хеши, использует кеш |

Команда `python3` в PATH должна указывать на Python 3.11+; `make build` затем
сам создаст отдельный venv. Например, штатный Python 3.9 на macOS для host CLI
недостаточен. Доверенный checkout scanner должен быть доступен оператору для
записи внутренних `.build/workflow` и `.build/artifact-cache`.

Инструмент не устанавливает системные пакеты через sudo, не перенастраивает
Docker context/daemon, CA/proxy или корпоративную PKI. Используются настроенные
оператором Docker endpoint и сборочная среда. Сканирование на удалённом daemon
не получает нового обещания поддержки локальных bind-путей: пути должны быть
доступны выбранному daemon; несоответствие даёт ошибку. Первичная приёмка —
локальный native Docker server Linux AMD64/ARM64; другие режимы требуют пилота.

## Команды

Makefile делегирует операции одному stdlib host CLI `./scanner`. Он находит
установку относительно своего файла, независимо от cwd входного проекта.
Существующие Python CLI и `scripts/docker_scanner.py` сохраняют свои контракты;
новое имя `scan` переводится в существующий `snapshot`.

| Make | Прямой CLI | Результат |
| --- | --- | --- |
| `make build` | `./scanner build` | Подготовленный и проверенный локальный комплект Analyzer/Scanner |
| `make scan REPO=...` | `./scanner scan --repo ...` | Полный snapshot выбранного коммита, default HEAD |
| `make diff REPO=... FROM=... TO=...` | `./scanner diff --repo ... --from ... --to ...` | Анализ перехода конечных состояний A/B |
| `make test` | `./scanner test` | Повседневные проверки проекта; точный suite реализуется на этапе 3 |
| `make help` или `make` | `./scanner --help` | Краткая справка без Docker, модели, сборок и сети |

Прямой CLI также имеет локальный `--version`. Неизвестные аргументы, лишние
позиционные значения, неоднозначные сокращения и неприменимые к операции
параметры отклоняются до контейнеров. Автоматических повторов scan нет.

### Параметры scan/diff

| Make variable | CLI | Default / правило |
| --- | --- | --- |
| `REPO` | `--repo` | Обязателен; self-contained локальный клон |
| `COMMIT` | `--commit` | Только scan; `HEAD` |
| `FROM`, `TO` | `--from`, `--to` | Только diff; оба обязательны, без неявного `HEAD~1` |
| `OUTPUT` | `--output` | Не задан: уникальный приватный каталог, см. ниже |
| `CONFIG` | `--config` | Не задан: текущие defaults анализа; поиск config в клоне отсутствует |
| `BASELINE` | `--baseline` | Только diff; не выбирается и не продвигается автоматически |
| `REQUIRE_BASELINE` | `--require-baseline` | Только diff; make принимает `0`/`1`, default `0`; CLI — флаг |

Пустое явно заданное значение пути/ref/config считается ошибкой, не default.
Относительные пользовательские пути разрешаются от cwd вызова, затем проверяются;
служебные пути — от доверенного корня scanner. Refs разрешает существующий Git
reader: tracked committed state, без checkout/fetch/хуков/фильтров и исполнения
кода проекта. Не включаются staged/untracked/working изменения.

`make scan REPO='/srv/git/example project' COMMIT=abc1234` и эквивалентный
прямой CLI обязаны давать одинаковую эффективную конфигурацию и отчёт.
Для shell пути с пробелами заключаются в кавычки. Присвоения make учитываются
только из его командной строки; одноимённые REPO/CONFIG/OUTPUT из внешнего
окружения не должны молча выбирать вход. HOME/XDG_STATE_HOME и стандартные
Docker-настройки имеют отдельно описанное служебное назначение.

Make передаёт значения как данные без eval, shell-конкатенации и повторного
раскрытия make/shell выражений. Исполняемые конструкции, управляющие символы
и небезопасные значения в make-вызове должны быть отклонены без выполнения;
для произвольных буквальных аргументов предназначен прямой CLI с argv.
Не вводится строка `ARGS` для выполнения произвольной shell-команды.

Явно указанные CONFIG/BASELINE — доверенные входы оператора; для Jenkins они
располагаются вне проверяемого workspace. Сканер не открывает автоматически
`.env`, Makefile, конфиги или baseline входного проекта. Приоритет анализа
остаётся CLI → явный JSON → defaults, как в [конфигурации](configuration.md).
Повторяемые include/exclude/encoding и остальные analysis flags доступны через
прямой CLI по существующему контракту; через make достаточно CONFIG для сложного профиля.

### Ресурсы и время

Дополнительные параметры не нужны в первом примере. Их значения и ограничения
наследуют [нынешний launcher](runtime.md), а не вводят новый набор настроек.

| Make variable | CLI | Default |
| --- | --- | --- |
| `ANALYZER_CPUS` / `SCANNER_CPUS` | `--analyzer-cpus` / `--scanner-cpus` | `2` / `1` |
| `ANALYZER_MEMORY` / `SCANNER_MEMORY` | `--analyzer-memory` / `--scanner-memory` | `3g` / `1g` |
| `RUN_TIMEOUT_SECONDS` | `--run-timeout-seconds` | `3600` |
| `STOP_GRACE_SECONDS` | `--stop-grace-seconds` | `30` |

Допустимые memory choices, положительность/конечность чисел, concurrency и
connect/analyze/ready deadlines сохраняются. Ресурсные параметры применяются
только к собственным контейнерам запуска; настройки daemon не меняются.

## Сборка, сеть и повторный запуск

`build` сначала проверяет предпосылки и `linux/amd64` либо `linux/arm64` выбранного
Docker server, включая aliases x86_64/aarch64. Затем автоматизирует существующую
цепочку: отдельное Python-окружение → pinned upstream prepare/verify → получение
артефактов/модели → Analyzer build/seal → engine → единственный wheel текущей
package version → Scanner build/deployment → verify и короткий synthetic smoke.
См. [карту переиспользования](../../verification/simple-workflow-stage-1/README.md#карта-существующего-маршрута).

Сеть разрешена для подготовки внутри явного build. Нет плавающего upstream main,
выбора соседнего checkout по его HEAD или обновления модели/dependencies «заодно».
Source lock сохраняет точный upstream commit. Build не вызывает целиком CI
`check_cpu_candidate.py`: его принудительный no-cache и полная приёмка не становятся
платой за обычную сборку. Подготовленный hash-cache, venv и BuildKit cache
переиспользуются после проверки; валидный неизменный комплект можно проверить и
переиспользовать без повторного получения/сборки. Повреждённые bytes не принимаются.

`build` не требует установленного dev venv от пользователя и не требует вводить
имя wheel или пути между шагами. Host bootstrap/dev dependencies остаются явно
закреплёнными. Незакоммиченные собственные изменения доверенного checkout не
выдаются за исходный commit: результат связывается с фактическими material inputs
и dirty-state. Build contexts остаются curated, без всего checkout, .env и секретов.

В минимальной внутренней структуре под `.build/workflow/` находятся окружение,
каталоги builds с уникальными ID и запись выбора текущего успешного комплекта
для конкретного daemon/platform. Существующий `.build/artifact-cache/` используется
повторно. Сгенерированный deployment лежит внутри своего build-каталога.
Это внутреннее состояние, не новые пользовательские конфиги.

Запись выбора переключается атомарно только после всех обязательных проверок.
Сбой/отмена оставляет предыдущую запись и её images доступными. Если исходники
уже изменились, сохранённый старый комплект не объявляется совместимым с новым
кодом: нужен успешный build либо возврат к соответствующему доверенному checkout.
Молчаливого downgrade нет. Параллельные builds
для одного daemon сериализуются; scan фиксирует один неизменяемый комплект и
не удерживает общую build-блокировку. Переключение не меняет комплект уже идущего
scan. Старые образы/каталоги и чужие Docker-ресурсы автоматически не удаляются.

Перед каждым scan сверяются платформа/daemon, запись успешной сборки, отпечаток
влияющих исходников и pins, deployment/engine и фактические локальные Image IDs.
Документационные изменения сами по себе пересборки не требуют. При изменённых
влияющих inputs, чужом daemon, удалённом image или несовместимом состоянии —
понятный отказ с предложением `make build`. Поиск «последнего каталога» по mtime,
fallback к ARM64 lock из Git, silent pull/build и исправление хешей запрещены.
Сгенерированная запись и её пути также проверяются как обычные доверенные файлы,
без ссылок/выхода из ожидаемого build-каталога и чтения state из input repo.

## Отчёты и жизненный цикл

Default root отчётов: `${XDG_STATE_HOME:-$HOME/.local/state}/ru-llm-scanner/reports`.
XDG_STATE_HOME, если задан, должен быть абсолютным. Новый run-каталог получает UTC
время и случайный ID. Инструмент создаёт свои отсутствующие служебные каталоги с
0700, файлы отчёта с 0600 и не меняет права уже существующих чужих путей.
Если root недоступен или оказался внутри input repo, нужен явный OUTPUT вне клона;
молчаливого fallback в cwd или `/tmp` для долговременных отчётов нет.

Явный OUTPUT — новый либо пустой приватный каталог с существующим parent,
принадлежащий оператору. Сохраняются проверки ссылок/пересечения с input/owner/
permissions; существующие отчёты не перезаписываются. Пути выводятся с безопасным
экранированием; находки, контекст, stderr процессов и ответы Analyzer в console
не печатаются. Отчёты не открываются браузером и не загружаются во внешние системы
автоматически. [Формат/coverage](reports.md) остаются прежними.

Launcher генерирует отдельный private Compose project с internal network,
read-only input/rootfs, non-root UID/GID, tmpfs, отключёнными logs и pull_policy never.
Сканер дожидается readiness, анализирует, публикует JSON/HTML и завершает только
свои ресурсы. SIGINT/SIGTERM, таймаут и отказ Analyzer проходят существующую
логику остановки/cleanup; infrastructure failure имеет приоритет над clean report.
Каждому параллельному scan принадлежат свои контейнеры, сеть и output.

Простой diff подтверждает изменённые файлы B. Только совместимый доверенный clean
baseline A и strict-проверка позволяют подтвердить неизменённые. Новый механизм/
profile требует нового полного clean snapshot, baseline не продвигается автоматически.
Промежуточная история A…B не проверяется. [Условия baseline](baseline.md).

## Результаты и диагностика

| Прямой CLI | Значение |
| --- | --- |
| scan/diff `0` | Заданная проверка завершена без находок |
| scan/diff `1` | Заданная проверка завершена с находками |
| scan/diff `2` | Ошибка/неполнота, даже при наличии находок |
| build/test `0` | Собственная операция успешно выполнена |
| build/test `2` | Ошибка подготовки/проверки; тестовые exit1 не означают пользовательскую находку |
| help/version `0` | Только локальная информация |

Для make успех рецепта —0, ошибка обычно приводит к собственному коду make2.
Нельзя использовать код make для различения находки и ошибки scan. В видимой
сводке сохраняется настоящий результат операции; Jenkins вызывает прямой CLI.
Консоль нового CLI — краткий читаемый текст на русском: стадия, счётчики, результат
и пути. Автоматизация использует код процесса и report.json, не парсит этот текст.
Внутренние поля `exit_code` и infrastructure `error` существующего launcher
сохраняются; его JSON-протокол не меняется. Оболочка не
исправляет report.json после сбоя. До создания отчёта ошибка может оставить
только диагностику; отсутствие отчёта не означает clean.

| Ситуация | Сообщение / действие |
| --- | --- |
| Нет Python/venv/Git/Make/Docker/Compose нужной версии | Назвать отсутствующий инструмент и требование; установить средствами администратора |
| Docker недоступен или нет прав | Проверить выбранный context/доступ; не переключать context и не выполнять sudo автоматически |
| Не поддержана архитектура или чужой комплект | Сообщить native CPU requirement и предложить сборку в подходящем окружении |
| Нет успешного build, stale state или images | «Установка не подготовлена/не соответствует исходникам. Выполните make build» |
| Build не получил pinned artifact или не прошёл hash/seal/smoke | Назвать стадию и безопасный код; прежняя установка сохранена, повторить после устранения причины |
| Нет REPO/ref или Git-объекта | Назвать параметр/код без исходных значений; проверить локальный клон/refs, без fetch |
| Непригодный output/root | Выбрать новый приватный OUTPUT вне клона; не chmod/чистить существующий каталог автоматически |
| Неверный CONFIG | Указать ошибку конфигурации; проверить явный файл и параметры, без echo содержимого |
| Нет/невалиден/несовместим baseline | Объяснить статус; выбрать доверенный baseline A либо сделать новый полный snapshot, без автоматического продвижения |
| Analyzer не готов/упал/timeout/OOM | Сообщить код, доступные пути отчётов и budgets; не публиковать container logs/входной текст |
| Отмена или cleanup failure | Вернуть2, показать безопасный код и own project identifier, сохранить имеющиеся приватные отчёты |

Расширенные реальные коды остаются в [справочнике ошибок](errors.md). Проверка
предпосылок встроена в операции; run_started/build_started/result и следующая
рекомендуемая команда выводятся без чувствительных значений. Необязательный
CONFIG не становится обязательным из-за диагностики.

## Jenkins: проектируемый пример

Пример предназначен для будущего интерфейса и ещё не является испытанным pipeline.
На агенте уже есть доверенная установка в `/opt/ru-llm-scanner`, подготовленная
тем же non-root оператором на этом daemon через build. Входной клон и report root
вне очищаемого workspace; конфигурация pipeline берётся из доверенного места.

```groovy
node('scanner-native') {
    int status = sh(
        returnStatus: true,
        script: '/opt/ru-llm-scanner/scanner scan --repo /srv/git/project --commit HEAD'
    )
    if (status == 1) {
        error('Scanner: обнаружены чувствительные данные; отчёт остаётся приватным')
    } else if (status != 0) {
        error('Scanner: проверка завершилась ошибкой или неполнотой')
    }
}
```

Реальное имя агента/пути выбирает администратор. JSON/HTML не публикуются через
archiveArtifacts автоматически. Strict diff требует явных FROM/TO, BASELINE и
REQUIRE_BASELINE; не заменять им полный первоначальный snapshot.

## Проверка готовности реализации

Достаточно получить первый отчёт после build и scan без JSON-редактирования,
проверить native AMD64/ARM64, точные коды прямого CLI и сохранность изоляции/старой
установки. Точные сценарии и распределение между этапами 2–4 приведены в
[матрице приёмки](../../verification/simple-workflow-stage-1/README.md#матрица-будущей-приёмки).
Этап39 проверял только спецификацию. Проверки реализации этапа40 фиксируются
отдельно; их результаты не означают приёмку будущего suite, нового Jenkins
pipeline или переноса обновлений proxy.
