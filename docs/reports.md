# JSON и HTML отчёты

Статус: JSON/HTML writer и runtime schema/semantic validation реализованы
на этапе 5. [JSON Schema](../schemas/report-v1.schema.json) использует
[Draft 2020-12](https://json-schema.org/draft/2020-12) и локальные `$defs`:
проверка схемы не требует сетевой загрузки `$ref`.

Внутренний [scan API](scan-api.md) уже формирует находки, полный манифест,
хеши, охват/ошибки и итог 0/1/2. Его `ScanResult`/`summary()` ещё не JSON-артефакт
v1 и не baseline. `reports.build_report` формирует валидируемый scan_report,
CLI сохраняет оба артефакта. [Запуск и ошибки записи](cli-quickstart.md). Если один обязательный слой файла завершился ошибкой,
незавершённые кандидаты этого файла отклоняются; находки завершённых файлов
сохраняются вместе с неполным итогом.

## Верхний уровень JSON

Все поля ниже обязательны. `null` допускается только там, где значение ещё
не получено при ошибке или неприменимо. Неизвестные поля writer v1 не пишет.

| Поле | Содержание |
| --- | --- |
| `schema_version` | `1.0.0` |
| `artifact_kind` | `scan_report` либо `contract_example`; пример не доказательство проверки |
| `report_id`, `created_at` | UUID запуска и время RFC 3339 с timezone, writer пишет UTC |
| `scanner.version` | Версия сборки scanner |
| `scan` | `mode`, введённые refs, полные target/base commit OID, target tree OID, object format |
| `configuration` | Полный эффективный профиль по [конфигурации](configuration.md), либо `null` при ранней ошибке |
| `engine` | Происхождение и подпись механизма, либо `null`, если не удалось их установить |
| `baseline` | Статус, требование strict, UUID/SHA-256 предъявленного артефакта и причины отказа |
| `coverage` | Полнота, завершённость перечисления, хеш манифеста и счётчики |
| `files` | Все недиректориальные записи B, включая исключения и неизменённые |
| `deleted_files` | Удалённые записи A без чтения их содержимого |
| `findings` | Все окончательные места обнаружения |
| `errors` | Безопасные коды/сообщения ошибок и связь с записью файла, если применимо |
| `result` | `status`, `exit_code`, `assurance`, `findings_count` |

В `engine` входят `scanner_semantics`, `profile_sha256`, `upstream_commit`,
`analyzer_image_digest`, `analyzer_signature`, `model_id`, `model_revision`,
`model_weights_sha256`, `patchset_sha256`, `dictionary_sha256`.
Digest образа записывается как `sha256:...`: это ID из платформенного inspect,
то есть digest конфигурации либо платформенного manifest в зависимости от
Docker image store. Общий multi-platform index для профиля не используется.
Остальные SHA-256 — 64 hex-символа.
Git OID — 40 либо 64 hex-символа согласно object format репозитория/артефакта.
Модель/upstream могут использовать SHA-1 независимо от формата сканируемого Git.

## Манифест и охват

Запись `files`: `id`, `path`, `path_bytes_b64`, `object_oid`, `mode`,
`size_bytes`, `change`, `previous_path`, `status`, `reason`, `encoding`,
`evidence_report_id`. Для недоступного размера/нетекстового объекта size может
быть `null`. У `inherited` encoding сохраняется из предыдущего отчёта.
`previous_path` — объект отображаемого/сырого пути только для `renamed`.

`coverage.counts` содержит `target`, `analyzed`, `inherited`, `unverified`,
`excluded`, `unsupported`, `error`, `deleted`. Сумма шести статусов равна
числу `files` и `target`. `deleted` равен длине `deleted_files`, остальные
счётчики — числу соответствующих статусов. `manifest_sha256` определяется
в [baseline](baseline.md); при незавершённом перечислении равен `null`.

`reason` отсутствует в смысловом отношении как `null` для успешного анализа;
для исключений/ошибок это строковый машинный код: например `path_excluded`,
`not_included`, `binary`, `pdf`, `office`, `image`, `archive`, `lfs_pointer`,
`submodule`, `symlink`, `decode_error`, `file_too_large`, `analyzer_timeout`.
`unverified` имеет `reason=no_baseline`. Код `error` в записи файла
сопровождается записью в `errors`. Каталог причин расширяется без переписывания
таблиц представления, как каталог категорий.

## Находка

| Поля | Правило |
| --- | --- |
| `id`, `file_id` | Детерминированные SHA-256, не случайные номера |
| `category` | Строка `UPPER_SNAKE_CASE`, новые upstream-категории допустимы |
| `path`, `commit` | Отображаемый путь и target commit B |
| `start_offset`, `end_offset` | `[start,end)` в code points исходного текста без BOM |
| `start_line`, `start_column`, `end_line`, `end_column` | Нумерация с 1, конец исключающий |
| `value` | Полное исходное найденное значение |
| `context` | `start_line`, `end_line` (включительно), `text` с исходными переводами строк |
| `source`, `score`, `rule_id` | Реальный источник, score `[0,1]`, известный rule ID или `null` |

`file_id = sha256(raw_path_bytes)`. `finding.id` — SHA-256 канонического JSON
объекта `{path_bytes_b64,object_oid,category,start_offset,end_offset,source,rule_id}`,
по правилам сериализации из [конфигурации](configuration.md). Идентификатор
стабилен для того же Git-содержимого, места и детектора, не зависит от run UUID,
контекста или сортировки. Отдельные повторные упоминания имеют разные смещения.
Изменение содержимого файла меняет ID, даже если видимое значение сохранилось.

Сортировка находок: сырые байты пути, start, end, category, source, rule_id
(`null` перед строками). Совпадающий стабильный ID дедуплицируется с максимальным
score. Разные категории/источники не теряются только из-за совпадения значения.
Upstream уже выполняет собственное слияние кандидатов: отчёт показывает его
окончательные сущности и словарные совпадения, не все внутренние сырые гипотезы.

Приватный ключ и другие многострочные значения сохраняются целиком.
`score` не является вероятностью действительности секрета. Коммит — состояние
проверки, поиск первого появления не выполняется. Правила Unicode/CRLF
и не-UTF-8 путей определены в [режимах](scan-modes.md).

## Итог

| `status` | Код | Значение |
| --- | --- | --- |
| `clean` | `0` | Нет находок, заданная проверка завершена |
| `findings` | `1` | Есть находки, заданная проверка завершена |
| `incomplete` | `2` | Работа началась, но обработка не завершена |
| `error` | `2` | Ошибка до содержательной проверки, например baseline/preflight |

При коде `2` `coverage.complete=false`, `assurance=none`, `errors` непустой;
уже найденные значения остаются в отчёте. При кодах `0/1` errors пустой,
перечисление завершено, profile и Git OID известны.

| `assurance` | На что распространяется результат |
| --- | --- |
| `snapshot_verified` | Поддерживаемая область полного снимка |
| `baseline_verified` | Область B с условным наследованием доверенного A |
| `changed_files_only` | Только выбранные изменённые файлы, чистота A не подтверждена |
| `none` | Проверка не завершена, подтверждения нет |

Находки и assurance независимы: завершённый snapshot с находками имеет
`snapshot_verified` как подтверждение области обработки, но не чистоты.
Новый baseline допустим только при чистом результате с достаточным assurance.

## Схема и смысловые проверки

Schema проверяет форму, типы, диапазоны, обязательность полей, сочетания
status/exit/assurance и базовые условия режимов. Автор и потребитель дополнительно
проверяют следующие инварианты; одна Schema их не доказывает:

1. Счётчики совпадают с массивами; ID и сырые пути уникальны, Base64 каноничен.
2. OID файлов/дерева соответствуют object format сканируемого репозитория;
   полный манифест совпадает с Git-деревом, хеш пересчитан.
3. Находка ссылается на `analyzed`-файл того же пути и коммита; `start < end`,
   диапазон и value совпадают с исходным текстом, координаты и контекст точны.
4. Ссылки на inherited evidence, статус baseline, profile и итог согласованы.
5. Перечисление неполно — manifest hash `null`; успешный результат не содержит
   необработанных выбранных файлов. В snapshot/verified diff нет `unverified`.
6. Engine profile пересчитан из фактических артефактов и настроек; успешный
   запуск не может подставить выдуманные provenance или источник.

Структурная проверка использует
[jsonschema с явным Draft202012Validator и format checker](https://python-jsonschema.readthedocs.io/en/stable/validate/).
В этапе 1 проверяются схема, примеры и доступные без Git/детектора инварианты;
остальные проверки реализуются и проверяются на последующих этапах.

Версия схемы отдельна от версии scanner. Writer следует точной схеме своей
версии. Baseline v1 принимает только явно поддерживаемую точную версию;
неизвестная версия отклоняется. Новые поля требуют опубликованной версии
схемы и проверки читателей; несовместимое изменение — новая major-версия.

## HTML и запись

`report.html` — представление того же результата, с фильтрами по
категориям/файлам/источникам, группировкой повторов и доступом ко всем местам.
Внешние CDN, fonts, скрипты и изображения не требуются. Текст, пути и значения
экранируются; данные не вставляются как исполняемый HTML/JS. Полные значения
могут быть чувствительными даже в ошибочном отчёте. Не загружайте их в Issues.

Ошибка построения/записи любого обязательного отчёта означает код `2`.
JSON по возможности сохраняет `report_write_error`, даже если HTML не создан;
успешно записанный отчёт не должен утверждать, что оба файла готовы, если это
не так. Контрактные JSON-примеры не являются результатами детектора. HTML QA выполнена
на настоящих синтетических артефактах [этапа 5](../verification/stage-5/README.md).
