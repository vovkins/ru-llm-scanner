# Сканирование локального репозитория

Это руководство для пользователя готового окружения. Администратор заранее
подготавливает образы и передаёт вам доверенный launcher, deployment lock и
параметры доступа. Сборка описана в [руководстве администратора](../admin/README.md).

## 1. Получить комплект и проверить готовность

На хосте нужны Python 3.11+ со стандартной библиотекой, Docker/Compose и
non-root учётная запись с доступом к Docker. Пользовательский venv, исходный
`ru-llm-proxy`, веса и Python-библиотеки на хосте для сканирования не нужны:
Analyzer, словарь и scanner уже внутри локальных образов.

Получите от администратора:

- каталог установки, например `/opt/ru-llm-scanner`, с `scripts/docker_scanner.py`;
- путь к выбранному доверенному `deployment.json` и подтверждение, что образы импортированы;
- путь к подготовленному клону, доступному Docker для read-only mount;
- доступный внешний каталог результатов и, при необходимости, одобренный config/baseline.

Ниже пути — примеры. Замените их своими значениями и выполняйте команды в
одной POSIX shell-сессии. Временные пути на macOS задавайте через `/private/tmp`,
если требуется временный каталог: `/tmp` является системной ссылкой.

```sh
cd /opt/ru-llm-scanner
SCANNER_LOCK=/srv/ru-llm-scanner/deployment.json
REPO=/data/project
RESULTS=/data/scanner-results

python3 scripts/docker_scanner.py verify --deployment-lock "$SCANNER_LOCK"
```

Готовность: команда завершилась **0** и вернула `{"exit_code": 0, "operation": "verify"}`.
`verify` проверяет локальные image IDs и платформу без запуска полного сканирования;
readiness модели проверяется при scan. Код 2 — повод устранить причину с администратором.
Не заменяйте ожидаемый ID вручную и не скачивайте `latest` для обхода отказа.

## 2. Выбрать коммит и каталог результатов

Вход — обычный самодостаточный Git-клон или bare-репозиторий. Нужные коммиты,
деревья и blobs должны уже находиться локально. Linked worktree, alternates и
внешняя Git metadata не поддерживаются; [точные требования](../git-reader.md).
Не изменяйте object store параллельно со сканированием.

Scanner читает **tracked Git-объекты указанного коммита**. Незакоммиченные,
staged и untracked файлы рабочей папки не входят в результат. Он не выполняет
checkout, fetch, хуки, фильтры или код проекта. `HEAD` допустим; для повторяемого
запуска лучше записать полный commit SHA. В отчёте сохраняется разрешённый SHA.

`RESULTS` должен заранее существовать и принадлежать вам. Output каждого
запуска должен быть новым либо пустым приватным каталогом вне клона.
Для первого запуска можно создать собственный родитель так:

```sh
mkdir -m 700 "$RESULTS"
```

Команда предполагает, что каталога ещё нет и его родитель доступен. Если он уже
создан администратором, проверьте доступ; не меняйте права чужих каталогов.
Конечный output должен принадлежать вашему UID и не иметь group/other permissions
(обычно `0700`). Symlink в пути, непустой, публичный или чужой output отклоняется.
Scanner не исправляет chmod/chown существующей папки. Файлы отчётов имеют `0600`.

## 3. Проверить один снимок

```sh
B=COMMIT_B
python3 scripts/docker_scanner.py snapshot \
  --deployment-lock "$SCANNER_LOCK" \
  --repo "$REPO" --commit "$B" --output "$RESULTS/snapshot-B"
SCAN_EXIT=$?
printf 'scanner exit: %s\n' "$SCAN_EXIT"
```

Замените `COMMIT_B` существующим SHA или ref; можно использовать `B=HEAD`.
Scanner проверит полное содержимое поддерживаемых текстовых файлов B. Команда
возвращает 1 при находках — это ожидаемый результат, который shell/CI должны
обработать явно. При `set -e` заранее предусмотрите обработку ненулевого кода.

В консоли launcher остаётся безопасная техническая сводка: `exit_code`,
`project` и `error`. В новом output обычно появляются `report.html` и
`report.json`. При раннем отказе или ошибке записи их может не быть.

| Код | Действие пользователя |
| --- | --- |
| `0` | Проверка завершена без находок в заявленной области; оцените coverage/assurance |
| `1` | Проверка завершена с находками; разберите все места в отчёте |
| `2` | Ошибка или неполнота, даже если найдены значения; исправьте причину и запустите заново в новый output |

Код 0 не гарантирует обнаружение всех секретов и не распространяется на
исключённые/неподдерживаемые объекты. [Каталог и известное качество](../reference/detection.md).

## 4. Прочитать HTML и JSON

Откройте `snapshot-B/report.html` локально в браузере. Сервер и интернет ему
не нужны. Работают поиск, фильтры по файлу/категории/источнику и группировка.
В карточке есть полное значение, путь, коммит состояния, строки/столбцы,
контекст, источник и score. Конец диапазона исключающий; строки/столбцы с 1.
Score — оценка распознавателя, не вероятность действительности секрета.

Оцените не только карточки, но и манифест файлов, ошибки и границы охвата:

| Статус файла | Что произошло |
| --- | --- |
| `analyzed` | Полный текст обработан сейчас |
| `inherited` | Подтверждение перенесено из совместимого доверенного baseline |
| `unverified` | Неизменённый файл обычного diff не проверен |
| `excluded` | Файл вне заданных include/exclude |
| `unsupported` | Содержимое вне текстовой области: например PDF, архив, LFS pointer, ссылка или подмодуль |
| `error` | Файл должен проверяться, но обработка не завершена |

`coverage.complete=true` означает завершённость **заданной** проверки. В diff
оно совместимо с `unverified > 0`; смотрите `result.assurance`. `snapshot_verified`
и `baseline_verified` подтверждают область обработки, а не отсутствие ошибок
самих детекторов. [Подробные режимы](../reference/scan-modes.md).

JSON предназначен для последующей обработки; структура и координаты описаны
в [справочнике отчётов](../reference/reports.md). Не заменяйте JSON HTML-страницей,
console summary или произвольно составленным файлом для baseline.

[Демонстрационный HTML](../../examples/demo/report.html) и
[его JSON](../../examples/demo/report.json) содержат только синтетические данные,
помечены `contract_example` и **не подходят как baseline**.

## 5. Проверить переход A → B

Если нужно обработать только изменённые файлы:

```sh
A=COMMIT_A
B=COMMIT_B
python3 scripts/docker_scanner.py diff \
  --deployment-lock "$SCANNER_LOCK" \
  --repo "$REPO" --from "$A" --to "$B" \
  --output "$RESULTS/diff-A-B"
```

Проверяется **полный файл B**, включая неизменённые строки изменённого файла.
Результат имеет `assurance=changed_files_only`: обычный diff не подтверждает
содержимое неизменённых файлов. A и B сравниваются напрямую, без merge-base.

Для подтверждения неизменённых файлов нужен доверенный чистый отчёт для **A**.
Сначала выполните snapshot A:

```sh
python3 scripts/docker_scanner.py snapshot \
  --deployment-lock "$SCANNER_LOCK" \
  --repo "$REPO" --commit "$A" --output "$RESULTS/snapshot-A"
```

Только после успешного кода **0** и сохранения обоих артефактов продолжайте:

```sh
python3 scripts/docker_scanner.py diff \
  --deployment-lock "$SCANNER_LOCK" \
  --repo "$REPO" --from "$A" --to "$B" \
  --baseline "$RESULTS/snapshot-A/report.json" --require-baseline \
  --output "$RESULTS/verified-A-B"
```

Baseline допускается только из завершённого запуска с кодом 0, достаточным
assurance и доверенным происхождением. Требуются тот же A/tree и полный профиль.
Находки, ошибки, другой коммит, модель/образ/словарь/score или scope делают
отчёт непригодным. Предъявленный неподходящий baseline даёт 2 даже без strict-флага;
скрытого перехода к обычному diff нет. После смены профиля сделайте новый snapshot.

При успешном clean diff B его отчёт может стать baseline следующего перехода
по правилам доверенного процесса. Не продвигайте файл только из-за надписи clean:
JSON и HTML публикуются атомарно **по отдельности**, общей транзакции нет.
При сбое один из файлов может отражать более раннее состояние; итоговый код 2
запрещает продвижение. [Полные условия baseline](../reference/baseline.md).

При A=B без baseline проверено лишь отсутствие изменений, `changed_files_only`.
С совместимым baseline сохраняется подтверждённый охват. Ни один вариант
не проверяет промежуточные коммиты: добавленный и удалённый между A/B секрет
может остаться в истории. Для CI проверяйте каждый принятый переход, а для
разового аудита используйте snapshot нужного состояния.

## 6. Настроить область и лимиты

Конфигурацию передавайте явно из доверенного файла вне клона. Автоматического
чтения `.env` или scanner config проекта нет. [Синтетический пример](../../examples/config/scanner.json)
показывает значения по умолчанию; копируйте его в каталог, контролируемый оператором.

```sh
python3 scripts/docker_scanner.py snapshot \
  --deployment-lock "$SCANNER_LOCK" \
  --repo "$REPO" --commit "$B" --config /data/trusted/scanner.json \
  --exclude 'generated/**' --encoding 'legacy/**=cp1251' \
  --max-file-bytes 10485760 --output "$RESULTS/configured-B"
```

Пример исключает `generated/**` из охвата и назначает кодировку `legacy/**`.
Выбирайте эти правила по содержимому своего проекта; они не рекомендуемые
универсальные исключения. Закоммиченные dotfiles, tests/vendor и `.gitignore`
автоматически не пропускаются. Слишком большой выбранный текст и decode/timeout
дают 2, а не чистый пропуск. Неподдерживаемые форматы остаются видимыми в манифесте.

Явные CLI-настройки заменяют соответствующее поле JSON; повторяемый параметр
заменяет весь список. Include/exclude/encoding/size/score меняют профиль и требуют
нового snapshot для baseline. Контекст и execution budgets сами по себе профиль
не меняют. Все defaults, glob/encoding правила — в [конфигурации](../reference/configuration.md),
container budgets — в [runtime](../reference/runtime.md).

## 7. Разобрать ошибку и сохранить результаты

| Ситуация | Следующий шаг |
| --- | --- |
| Не найдены ref/object | Проверить SHA и подготовить недостающие объекты доверенным SCM-процессом; scanner сам не fetch-ит |
| Output/права/запись | Проверить owner, отдельный новый 0700 output, свободное место и доступ Docker к пути |
| Baseline отвергнут | Проверить A/tree/profile и происхождение; при смене профиля сделать snapshot |
| Analyzer/image/readiness | Передать администратору безопасный код/project и параметры среды без содержимого отчёта |
| Decode/size/timeout | Проверить конкретную причину в JSON; согласовать кодировку/лимит и запустить заново |

Подробная [диагностика администратора](../admin/operations.md) различает
инфраструктурные ошибки launcher и ошибки внутри report. При коде 2 сохранённые
находки всё равно требуют внимания, но отсутствие карточек не подтверждает clean.

**JSON/HTML содержат значения и контекст полностью.** Храните их в приватном
каталоге, ограничивайте доступ CI/artifacts/backups и срок хранения. Передавайте
только по согласованному защищённому каналу. Не вставляйте отчёты и реальные
значения в публичные Issues, console или сервисы просмотра HTML. Удаление локальной
копии не удаляет архивы и backups; за них отвечает процесс организации.
[Сообщение о проблемах](../../SECURITY.md) должно быть обезличенным.
