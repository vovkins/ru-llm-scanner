# Корпус исходников code-v1

`code-v1.json` — независимый небольшой синтетический корпус этапа 4:
исходники, конфигурации, HTTP/CSV и документация. Он не заменяет upstream
корпус `ner_migration` и не копирует его результаты как метрики кода.

46 случаев содержат 37 размеченных мест всех 30 категорий Analyzer и
`DICTIONARY_TERM`, повторы, многострочный блок ключа, Unicode/CRLF, длинный
файл с находкой в хвосте и 12 отрицательных примеров. Входы созданы для теста,
не получены из пользовательских репозиториев или действующих сервисов.
Идентификаторы/реквизиты с контрольными суммами сгенерированы как искусственные
значения; имена не относятся к установленным субъектам. Block PRIVATE KEY —
неполный фиктивный PEM, JWT имеет фиктивную подпись. Их действительность
не проверяется никакими внешними запросами. Словарь содержит публичные названия
банков, которые исходный proxy считает защищаемыми терминами.

Разметка `{{CATEGORY:value}}` задаёт эталонное значение. Loader удаляет только
маркеры, сохраняя текст, и вычисляет fixture offsets. `prefix_repeat` задаёт
длинный текст без помещения повторов в JSON. Путь служит только синтетической
Git-записью; файлы/код корпуса не исполняются. Группы: credentials,
infrastructure, contact, identity, documents, financial, dictionary, negative.

Два разных результата проверки:

- Техническое соответствие: pipeline должен вернуть те же места/категории/
  sources/rules/score, что прямой Analyzer и исходная словарная политика при
  том же входе и профиле. Координаты/value дополнительно проверяются.
- Качество текущих детекторов: точные TP/FP/FN и precision/recall относительно
  независимой разметки, а также покрытие значений сущностью той же категории.
  Неточные границы считаются ошибкой exact match. Дополнительные категории,
  например LOCATION внутри адреса, видны как extra, если они не размечены.

Статус технического прогона `passed` не означает 100% качества детекторов.
Пропуски и ложные срабатывания сохраняются по case/category/offset, без
публикации найденных значений в служебных отчётах. На этом этапе не меняются
upstream-модель, правила, пороги и allowlist ради прохождения корпуса.
Изменение разметки после просмотра результатов требует явного объяснения,
а изменение области/приёмки — согласования по правилам проекта.

Повторение реальной проверки описано в [scan API](../../docs/scan-api.md),
[измерения и ошибки](../../verification/stage-4/README.md) сохранены отдельно.
Пользовательские scan-отчёты HTML/JSON и baseline относятся к этапу 5.
